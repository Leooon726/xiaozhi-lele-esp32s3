# 开发端与实机端 Agent 交接

开发端在远程 Linux 机器修改代码、测试、编译和准备固件；实机端在用户的
Mac（或其他连接设备的电脑）下载固件、备份、烧录、串口采集并协助用户验收。
两端通过 Git 中的状态与测试记录交接，不依赖另一段聊天历史。

## 从哪里知道当前进度

| 文件 | 职责 |
|---|---|
| [TESTING.md](TESTING.md) | 当前功能状态、待测试项目、版本记录索引；接任务先读 |
| `testing/<release-tag>.md` | 某一固件包的身份、测试计划和实际结果；新测试事实写在这里 |
| [testing/TEMPLATE.md](testing/TEMPLATE.md) | 每版交接记录模板，复制后填写，不在模板内记录真实结果 |
| [HANDOFF.md](HANDOFF.md) | 架构约束、项目背景和既有交接历史 |
| [VALIDATION.md](VALIDATION.md) | 既有验证历史；新版本通过 TESTING 中的链接查具体记录 |
| [TODO.md](TODO.md) | 需求与专项检查清单，勾选必须能追溯到测试记录 |

新结果以对应版本记录为依据，总表只概括并链接，不复制全部日志。功能说明
文件负责描述行为，不能用其中旧版“通过”替代新版验收。`BASELINE.json` 是旧
基线快照，含早期 128 首曲库等历史数据，不代表设备此刻状态。

## 开发端交出一个版本

1. 同步代码，查看 `git status --short`，保留用户未提交的工作。为新增功能在
   TESTING 功能表分配固定编号，分别记录源码、主机验证和实机验证状态。
2. 固件从已提交、无受跟踪文件改动的源码构建；记录完整 commit SHA、变体、
   SDK 和组件锁摘要。完成相关回归、完整编译、容量及打包校验；skip 单列。
3. 为这个源码提交准备唯一标签，约定 `test-<短SHA>-<序号>`，例如
   `test-abcdef123456-01`（仅命名示例，不表示已有该 Release）。同一源码
   重新构建、附件内容变化或构建参数变化都使用新序号，不替换已交付附件。
4. 复制模板到 `testing/<release-tag>.md`，填入完整源码 SHA、附件及 SHA-256、
   已通过的主机验证、已知问题，按功能 ID 写清每条实机操作及预期结果。
   所有尚未执行的实机项目标为“未测”，指定下一步由实机端执行。
5. 测试包必须保留 `flasher_args.json` 和它引用的五文件相对路径，并附构建
   manifest/校验值。当前 `build.py --zip` 仅打包合并镜像，不能直接充当此包；
   五文件测试包自动生成/发布尚未实现，不要把本协议描述成已有自动化。
6. 获得本次发布授权后上传 GitHub Pre-release，标签明确指向固件源码 SHA，
   不是随后更新交接文档的提交。上传完成并核对附件后才填真实 Release URL、
   发布状态和下载命令；之前保持“未发布”，不能让实机端下载不存在的版本。
7. 提交并推送交接记录及 TESTING 索引。Release 说明链接到该记录；以后实际
   测试结果在 Git 中维护，Release 说明只作为交付入口。已验收包是否转正式
   Release 由用户决定，不自动等同于“所有功能全部通过”。

创建记录后只更新文档无需重新构建固件；**固件源码 SHA、交接文档提交和最后
刷入设备的 SHA 是三个不同概念**。记录必须分别能追溯，不能拿 main 最新提交
推断包内容或设备版本。

## 实机端接收与回填

1. 保留本地改动后同步仓库（干净工作区可 `git pull --ff-only`），读 AGENTS、
   本协议、TESTING 和指定版本记录。不擅自选择最新 Release 或换用其他包。
2. 仅为串口工具准备 Python 环境，见 BUILD_FLASH；无需安装完整 ESP-IDF。
   用记录中的明确标签和附件名下载到 `.local/firmware/<tag>/`，校验包和
   五文件摘要、变体及分区设置。缺文件、摘要不符或版本对应不明时暂停烧录。
3. 获得用户当次烧录授权，使用 `device.py flash --build <五文件目录>
   --confirm-write`，先完整 16 MiB 备份和设备端校验，再五文件写入并检查
   NVS 保留。分区不匹配时走单独迁移评审，不改脚本强行绕过。
4. 记录实际刷入的包及 app 摘要、备份/写入/启动结果；若尚未刷入，设备状态
   继续写旧版或“未知”。下载成功、构建通过、烧录通过、启动正常均不等于
   触摸、声音、USB 读写等功能已验收。
5. 按测试 ID 逐项填实际结果。用户参与的物理观察注明“用户确认”和具体范围；
   Agent 看到串口状态只能报告该证据。打开串口可能复位，检查后释放端口。
6. 在对应版本记录追加带日期、执行者和环境的测试轮次；说明未测/失败/阻塞
   项以及下一步。提交并推送结果，再把记录路径或提交号交给开发端。
   若当前环境未授权推送，先保留本地提交并明确告知尚未同步。

开发端收到回填后先同步代码，按证据更新 TESTING 总表和相关 TODO；失败需要
新修复提交及新测试包，再在新记录引用旧测试 ID。旧版失败记录保留，不改成
通过。两端并发写文档出现冲突时保留双方测试轮次，不 force push 或丢弃记录。

## 状态和证据规则

- 源码状态：未实现 / 开发中 / 已实现；主机验证：未跑 / 通过 / 失败 / 有跳过。
- 每条实机用例：未测 / 通过 / 失败 / 阻塞 / 不适用。“不适用”必须有理由，
  不计为通过；“部分通过”仅用于汇总，具体哪些用例未通过必须能查到。
- Release 发布状态（未发布 / Draft / Pre-release / 正式）与测试结果分别记录。
  标为 Pre-release 不是“未测”的证明，转正式也不是“全测通过”的证明。
- 后续版本不能自动继承旧版通过；要么重测并记录，要么写“仅历史版本已验证，
  本版未复测”。已关闭的问题在新版本复现，新增回归记录，不覆盖旧证据。
- 只有启动或笼统“没问题”时，按实际覆盖范围记录，不扩大成全部专项通过。
  缺少证据时写“未知/待确认”，不从聊天猜测设备版本和 Release 标签。
- Git 和 Release 只放可公开的源码、测试包与脱敏结果。完整 Flash/NVS 备份、
  设备标识、用户歌单和原始串口日志只留执行机器 `.local/`；公开记录只写
  脱敏摘要，私有日志路径只能用于该机器本地追溯。

## 一次交接的最小消息

开发端：`版本标签 + 记录路径 + 源码SHA + 待测ID + 已知问题 + 下一步执行者`。

实机端：`版本标签 + 结果提交号 + 实际刷入版本 + 通过/失败/未测ID + 下一步`。

双方先以仓库记录接续，聊天消息只是入口；收到旧消息时仍核对仓库中的新结果。
